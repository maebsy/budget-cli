# 성능 측정과 병목 분석

`python scripts/benchmark.py` 로 거래 1천 / 1만 / 10만 건에서 명령별 시간과 최대 메모리를 측정했습니다.
시간은 메모리 추적 없이 따로 재고, 메모리는 `tracemalloc` 으로 측정했습니다.

- 환경: Python 3.10.20, Linux (클라우드 VM). 절대값보다 **건수에 따른 증가 추세**를 보는 용도입니다.
- 데이터: 5년치 무작위 거래, 카테고리 7종, 태그 5종 (`random.Random(42)` 고정 시드)

## 결과

| 작업 | 1천 건 | 1만 건 | 10만 건 (20.5 MB) | 10만 건 최대 메모리 |
| --- | ---: | ---: | ---: | ---: |
| `list --limit 20` (스트리밍 + 크기 20 힙) | 7.5 ms | 80 ms | 808 ms | **59 KB** |
| [비교] 파일 전체를 `list()` 로 로드 | 8.9 ms | 83 ms | 984 ms | **61,707 KB** |
| `search --category food --tag tag1` | 7.7 ms | 83 ms | 947 ms | 1,894 KB (일치 건만 보관) |
| `summary --month 2022-06` | 11.8 ms | 103 ms | 975 ms | 49 KB |
| `add` (다음 id 계산 포함) | 5.4 ms | 45 ms | 494 ms | 48 KB |
| `update` (임시 파일 → 원자적 교체) | 16.9 ms | 170 ms | 1,716 ms | 65 KB |
| `delete` (임시 파일 → 원자적 교체) | 17.9 ms | 166 ms | 1,752 ms | - |

## 해석

**메모리는 건수와 무관하게 일정합니다.** 10만 건에서 `list --limit 20` 은 59 KB 로, 전체를 리스트로 올리는 방식(약 60 MB)의 1/1000 수준입니다.
제너레이터가 한 줄씩 넘겨주고 `heapq.nlargest(20, …)` 가 상위 20개만 들고 있기 때문입니다. 1천 건 → 10만 건으로 데이터가 100배 늘어도 메모리는 55 KB → 59 KB 입니다.

**시간은 건수에 비례(O(n))합니다.** 모든 명령이 파일을 처음부터 끝까지 한 번 읽기 때문입니다. 1만 건까지는 0.2초 이내라 체감되지 않지만, 10만 건에서는 조회 약 1초, 수정·삭제 약 1.7초가 걸립니다.

## 10만 건에서의 병목과 개선 방향

| 병목 | 원인 | 개선 방향 |
| --- | --- | --- |
| 조회·요약이 매번 전체 파일을 파싱 | JSONL 은 인덱스가 없어 "2022-06 거래만" 같은 질의도 전부 읽어야 함 | **월별 파일 분할** (`transactions/2022-06.jsonl`) → summary 는 한 파일만 읽음. 또는 월별 합계를 캐시 파일에 미리 집계 |
| `update`/`delete` 가 파일 전체를 다시 씀 | 줄 길이가 달라 중간 수정이 불가능 | 삭제는 **톰스톤(삭제 표시) 줄을 append** 하고 주기적으로 압축(compaction). 수정도 새 버전을 append 하는 로그 구조로 전환 |
| `add` 가 다음 id 를 위해 전체를 훑음 | 마지막 id 를 따로 저장하지 않음 | `meta.json` 에 `next_id` 카운터 저장 (원자적 교체로 갱신) → O(1) |
| id 로 한 건 찾기 (`get`) | 선형 탐색 | id → 파일 오프셋 인덱스 파일. 근본적으로는 **SQLite**(표준 라이브러리 `sqlite3`)로 이전하면 인덱스·트랜잭션을 그대로 얻음 |

### 개선안별 난이도와 데이터 이전 주의점

| 개선안 | 기대 효과 | 난이도 | 위험 | 데이터 이전(마이그레이션) 주의점 |
| --- | --- | --- | --- | --- |
| `meta.json` 에 `next_id` 카운터 | `add` O(n) → O(1) | 낮음 | 카운터와 실제 최대 id 가 어긋나면 id 중복 | 처음 한 번 전체를 훑어 카운터를 만듦. 어긋남에 대비해 "전체 스캔으로 다시 만들기" 명령과, 쓸 때 중복 id 검사를 함께 둠 |
| 월별 합계 캐시 파일 | `summary` 가 캐시만 읽음 | 중간 | 거래 수정 · 삭제 · import 때 캐시 갱신을 빠뜨리면 틀린 합계 | 캐시는 언제든 지우고 다시 만들 수 있는 파생 데이터로 취급(원본은 거래 파일). 갱신 경로가 `rewrite` · `append` 두 곳뿐이라 거기서만 무효화 |
| 월별 파일 분할 (`transactions/2022-06.jsonl`) | 월 조회 · 요약이 한 파일만 읽음 | 중간 | 날짜를 바꾸는 `update` 가 두 파일에 걸침(한쪽만 바뀌면 거래가 사라지거나 중복) | 일회성 변환 명령 필요. 변환 전 `backup` 필수, 새 폴더에 다 만든 뒤 폴더째 교체해 도중 실패 시 원본 유지. id 는 파일 경계를 넘어 유일해야 함 |
| 톰스톤 append + 주기적 압축 | `update`/`delete` 가 전체 재작성 → 한 줄 추가 | 높음 | 모든 읽기 코드가 "같은 id 의 마지막 줄이 최신, 삭제 표시는 건너뜀" 규칙을 지켜야 함. 압축 도중 실패 | 파일 형식이 바뀌므로 레코드에 버전 필드 추가. 압축은 지금의 원자적 교체(`rewrite`)를 그대로 재사용 |
| id → 오프셋 인덱스 파일 | `get` 선형 탐색 → 바로 찾기 | 높음 | 재작성 때마다 오프셋이 전부 바뀌어 인덱스가 쉽게 낡음 | 인덱스도 파생 데이터로 두고, 크기 · 수정 시각이 다르면 다시 만듦 |
| SQLite(`sqlite3`)로 이전 | 인덱스 · 트랜잭션 · 부분 수정을 한 번에 | 중간 (코드량은 크지만 검증된 기능 사용) | 저장소 계층 전체 교체, JSONL 의 "사람이 열어 보기 쉬움"을 잃음 | `export`/`import` 경로로 옮기면 검증 로직을 그대로 탐. 이전 후에도 JSONL 내보내기를 남겨 되돌릴 길 확보 |

**권장 순서**: 위험이 낮고 효과가 분명한 `next_id` 카운터부터 넣고, 그다음 월별 합계 캐시를 넣습니다. 데이터가 계속 늘어날 것이 확실해지면 파일 분할이나 톰스톤 대신 SQLite 로 이전하는 편이 낫습니다. 직접 인덱스와 압축을 만드는 일은 SQLite 가 이미 해 주는 일을 다시 만드는 것이기 때문입니다. 저장소 계층(`storage.py`)만 바꾸면 되도록 계층을 나눠 둔 것이 이때 효과를 냅니다.

이번 과제는 "파일 기반 저장 + 스트리밍"을 익히는 것이 목적이라 단일 JSONL 을 유지했습니다.
대신 측정으로 한계 지점(약 10만 건에서 1초대)을 확인해 두었고, 다음 단계로 무엇을 바꿔야 하는지 위 표로 정리했습니다.

## 측정 중 발견해 개선한 점

처음 구현한 `update`/`delete` 는 "id 존재 확인" 을 위해 파일을 두 번 더 읽었습니다(서비스에서 한 번, 저장소에서 한 번, 재작성 한 번 = 3회 순회).
지금은 **재작성하면서 동시에 찾고**, 끝까지 못 찾으면 제너레이터가 `NotFoundError` 를 던집니다. 그러면 `JsonlFile.rewrite()` 가 임시 파일만 지우고 원본은 그대로 두므로,
안전성은 그대로 유지하면서 순회를 1회로 줄였습니다(`storage.py::TransactionRepository.update`).
